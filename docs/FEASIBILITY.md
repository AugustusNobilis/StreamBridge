# Technical feasibility audit

Audit date: **2026-10-14** (Europe/Moscow). Baseline: OBS **32.0.4** source; local runtime: **32.1.2 x64**, Qt 6.8.3, MSVC 2022. The public OBS documentation currently describes 33.0; all symbols used by this project were checked against the 32.0.4 headers. This document is not a declaration that the complete product passes acceptance.

## Evidence and decisions

| Requirement | Evidence | Decision / validation |
|---|---|---|
| One encoder, two outputs | Public `obs_output_set_video_encoder`, `obs_output_set_audio_encoder`; encoder implementation keeps per-output packet callbacks, begins capture for the first, ends for the last | Plugin owns one video/AAC pair. **Executed** with real x264/AAC and two instrumented libobs outputs: shared pointers, packets, stop/rejoin and reconnect passed. Real RTMPS transport also passed on 2026-10-14; see TEST-RESULTS.md. |
| Independence from OBS streaming | `obs_output_create`, `obs_service_create`, `obs_get_video`, `obs_get_audio` | Production code does not control standard streaming or alter its profile. Executed inside OBS 32.1.2: standard frontend Start/Stop against local RTMP coexists with two instrumented plugin sinks, separate encoder ownership and active OBS exit. Manual button/visual acceptance remains distinct. See TEST-RESULTS.md. |
| Different bitrate/resolution | Separate encoder instances, `obs_encoder_set_scaled_size` before initialization | Executed: 700/300 kbps profiles, 640×360 and 320×180, actual encoded packets. Hardware-specific availability still needs NVENC/AMF/QSV machines. |
| Different FPS | `obs_encoder_set_frame_rate_divisor` in OBS 32.0.4 public header | Only integer divisors 1–6; UI displays resulting FPS, never offers arbitrary rates. Executed with 30 and 15 FPS. 60/50 and 60/24 are not representable by this implementation. Changing OBS base FPS requires stopping StreamBridge. |
| Encoder settings | Public properties contain typed controls and allowed choices | H.264 and AAC only in this milestone. Rate control/preset lists come from encoder properties; unsupported controls are disabled. No borrowed OBS encoder or service setting mutation. SDR only; HDR is explicitly rejected before creating encoders. |
| YouTube desktop OAuth | Google native app Authorization Code + S256 PKCE, loopback redirect; Live Broadcast/Stream API | Feasible with a registered Desktop client, consent screen and approved scopes. No confidential secret belongs in the DLL. Implemented with mocked protocol tests; registered-client acceptance pending. Manual mode independent. See OAUTH.md. |
| Twitch OAuth | Official Device Code Flow supports registered **public** clients and secretless refresh. Stream-key API requires `channel:read:stream_key` | Use Device Code Flow, not a made-up PKCE variant. Handle polling interval, expiry, `slow_down`, refresh rotation and validation. Implemented with mocked protocol tests; real-account acceptance pending. |
| Existing OBS browser per-source proxy | `obs-browser/obs-browser-source.cpp` passes `nullptr` for request context when creating a browser. `browser-app.cpp` uses global context. Public OBS Browser API does not expose each source's CEF context | Do not modify existing browser/global proxy settings or load a second CEF runtime into OBS. Choose a separate CEF helper per source. |
| Own CEF request context | CEF 154 `CreateContext`, preference API and separate sandboxed processes | Implemented and exercised: two independently proxied helpers plus direct control, then three authenticated HTTP/HTTPS/SOCKS5 helpers with real HTTPS/WSS. Failure leaves the peer working and produces no successful direct reload. Full packet audit remains a release gate. |
| SOCKS5 authentication | Chromium explicitly supports no SOCKS5 authentication and only TCP URL traffic; destination DNS is resolved at the proxy | Loopback adapter must implement RFC1928 CONNECT with domain address and RFC1929 auth upstream. ## Existing projects and licenses

The official [obs-plugintemplate](https://github.com/obsproject/obs-plugintemplate) was inspected: CMake, Windows dependency bootstrap, locale/module structure and MSVC workflow. Its current buildspec targets OBS 31.1.1, so copying it unchanged would not meet this project's baseline. This repository uses its own smaller Windows-only CMake project and builds the official OBS 32 SDK rather than inventing headers/imports.

[obs-multi-rtmp](https://github.com/sorayuki/obs-multi-rtmp), inspected version 0.7.4.4, has a GPL v2 license and GPL-2.0-or-later notices in the template-derived files. It already offers useful encoder/output handling, but its `push-widget.cpp` includes pathways retrieving the frontend streaming output. Reusing it would require reviewing every retained file, changing encoder ownership, secret persistence and lifecycle, and adding an unrelated browser subsystem. For two fixed destinations, a small new libobs module is easier to audit. **No implementation code was copied from obs-multi-rtmp or obs-browser.** Their source snapshots are excluded build research material under `.deps`.

OBS is GPL-2.0-or-later. Our new code is GPL-2.0-or-later; LICENSE contains GPL v2. Qt Core/Gui/Widgets/Network may be used under LGPLv3 with applicable obligations; distribution of the combined work must use the GPLv3-or-later option when required for compatibility. The source's “or later” grant permits this; it does **not** mean the binary is necessarily distributable under GPLv2-only. Qt/OBS DLLs are supplied by OBS, not bundled in this plugin installer. CEF 154 is pinned by SHA-256; its exact BSD LICENSE.txt and complete Chromium CREDITS.html are packaged. NSIS compiler/stub licenses are described in THIRD_PARTY_NOTICES.md. Final public distribution review remains a maintainer gate.

## Browser experiment and remaining acceptance

The routing POC preceded source registration. It renders a real page and widgets with images, WSS, workers, redirects, animation and audio. Two independently logged proxies and a direct helper control passed; a three-protocol HTTPS/WSS test also passed. A STUN canary initially found a leak: the headless force flag alone was ineffective. The Chrome-runtime switch and request-context WebRTC preference applied before navigation fixed that regression. A local authoritative DNS fixture and full process-attributed DNS/DoH/IPv4/IPv6/QUIC traces remain necessary; a canary or IP page is insufficient.

The implemented design uses one sandboxed helper per source with no shared profile, fixed proxy before navigation, no `DIRECT`/PAC fallback, removed loopback bypass, and disabled QUIC/non-proxied WebRTC. These controls have specific runtime evidence, **not an exhaustive leak-freedom guarantee**. If further traffic escapes, require narrowly scoped process isolation or withhold stable release. Never change Windows routes or system proxy. Fail closed is mandatory in proxy mode; proxy-off is an explicit user choice.

Use authenticated, ACL-restricted IPC, random per-launch nonce and bounded validated frames/audio queues; no secret in argv/environment/logs. Adapter listens on 127.0.0.1 only with a per-helper capability, never a public listening socket. Authenticate only requests from the expected helper and reject malformed CONNECT requests. Pin HTTPS proxy certificate verification, tunnel TLS opaquely, resolve the destination remotely with SOCKS5. Resolution of a user-specified proxy hostname is distinct from destination DNS; offer a literal proxy IP when local resolution must be avoided. Kill the process tree on source destruction. Browser crash must leave a blank/error source, not kill OBS or trigger direct fallback.
